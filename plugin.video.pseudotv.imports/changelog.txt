- Slot/file duration fix — closes the root cause of the dead-zone class of bug that imports.47's loop-breaker contained. The 2026-05-22 schedule audit found 61 programmes on 5 channels where the EPG slot length (set from library `runtime`) exceeded the actual playable file duration: worst case "Five Fingers of Death" giving a 79-min film a 105-min slot = a 25-min dead zone; "Cartoon Network" giving ~44-min cartoons a 60-min slot = ~15-min dead zone; "Adult Swim", "Saturday Morning TV", "Marvel TV" similar. After imports.47 those channels stopped *flickering* during the dead zone but the operator still saw a loading screen for the full gap. Investigation: `addScheduling` (builder.py:956) is literally `stop = start + duration` with NO round-grid math anywhere in the codebase — no MOVIE_SLOT_LENGTH/BLOCK_LENGTH constants, no per-channel slot-length field. The 105-min and 60-min slots come from `fItem['duration']`, set by `jsonRPC.getDuration()` (jsonrpc.py:455). `getDuration` is gated on the existing `Duration_Type` setting: 0 = "quick" (return library `runtime` field — the scraped "official" runtime, often including credits/commercials the actual file does NOT contain), 1 = "accurate" (ffprobe the file). Operator was at `Duration_Type=0` so the slot used the scraped 105-min figure while the file plays for 79 min, leaving 25 min of dead air. **The latent issue:** even flipping `Duration_Type=1` to opt into ffprobe would NOT have fixed the worst cases because of a 25% sanity-check fallback inside `__parseDuration` (jsonrpc.py:477): `if round(percentDiff(runtime, duration)) > 25: duration = runtime`. The arithmetic: percentDiff(6300, 4763) = 32.3% > 25 → falls back to 6300 (the wrong library value); percentDiff(3600, 2663) = 35.2% > 25 → falls back to 3600; percentDiff(6060, 5298) = 14.4% ≤ 25 → ffprobe wins, but only the smaller mismatches. The check was defensive against ffprobe returning garbage on unsupported codecs, but the assumption "if ffprobe disagrees a lot, library is more correct" is exactly wrong when the library has a scraped runtime that includes content the file doesn't. **Five-line fix** in `resources/lib/jsonrpc.py`: (1) add `accurate=False` kwarg to `__parseDuration`'s signature, (2) `getDuration` passes its `accurate` flag through to `__parseDuration` in the non-stack branch (`else: duration = self.__parseDuration(runtime, path, item, save, accurate)` — stack branch deliberately untouched, preserves exact prior behaviour for stacked-file channels), (3) the `percentDiff > 25` fallback is now gated on `not accurate` so when the operator explicitly opts into ffprobe mode the value is trusted — the library `runtime` is the unreliable input we're trying to correct, (4) added a defensive `duration > 0` guard to the `queDuration` call so a failed ffprobe (returns 0) doesn't blast a 0 runtime into the Kodi library via JSON-RPC `SetXxxDetails`, (5) log line gains `accurate = %s` for forensics. **No new state, no new threads, no new locks, no new settings, no new strings.** All the levers already exist: the `Duration_Type` setting (settings.xml, label #30049), the `Store_Duration` setting (write ffprobed value back to library — opt-in by operator since it mutates state other addons may rely on), and the `DurationOptions` rule (rules.py:1120, id 500) which lets operators apply accurate mode per-channel via the dashboard at `:50002/manager.html` → channel Edit → Rules. **DELIBERATE non-changes**: (a) `builder.py`/`addScheduling` not touched — the slot computation was correct all along; the input was wrong. (b) `fillers.py` not touched — filler extends the channel timeline (each pre/post-roll item is a SEPARATE scheduled item with its own slot, not padding inside an existing slot), which is exactly the right behaviour now that slot ≈ file. (c) Stack-handling branch in `getDuration` (line 461) calls `__parseDuration(runtime, file)` without `accurate` and without `item`/`save`/`accurate` kwargs — keeps using the default `accurate=False` so stacked-file channels (concert.mkv split across two files etc.) have exactly the same behaviour as pre-imports.48. The latent bug where each segment's ffprobe is compared against the WHOLE stack's runtime (always falls back due to ~100% disagreement) is left for a future cycle if anyone hits it — no observed user impact. (d) `_getRuntime`'s 5-level fallback chain (jsonrpc.py:440) untouched. (e) No changes to `Duration_Type` schema default or `Store_Duration` schema default — operator opts in explicitly. (f) No changes to the loop-breaker / watchdog supervisor (imports.47); that's the runtime safety net and stays in place as defense in depth even when slots now match files. **Latent runtime=0 bug noted but out of scope**: when library `runtime=0`, `getDuration` falls through to ffprobe regardless of accurate mode. With ffprobe returning a positive value, `percentDiff(0, positive) = 100% > 25` (with accurate=False) → falls back to 0 → `getDuration` returns 0 → `builder.py:909`'s `if dur > self.minDuration` skips the file. Files with no library runtime get silently dropped. Pre-existing bug, not caused by this work, not user-observed; fixing it would silently surface previously-invisible files which is its own decision. **12 new pytest cases in `tests/test_get_duration_accurate.py`**: mirror-and-test pattern (jsonrpc.py not trivially importable; mirror inline like `test_chkcallback_cas.py` / `test_transition_supervisor.py`). Behavioural tests cover accurate=True with large disagreement (FFOD case, regression guard), accurate=True with small disagreement (sanity), accurate=True for the Cartoon Network case, accurate=True+save with ffprobe value written back via queDuration, accurate=True with ffprobe failure (returns 0) NOT writing a 0 to queDuration, accurate=False with large disagreement falling back to runtime (existing conservative behaviour preserved), accurate=False with small disagreement using ffprobe, accurate=False with ffprobe=0 falling back to runtime. Source-scan tests guard against drift between mirror and production: `__parseDuration` signature includes `accurate=False`; `getDuration` passes `accurate` through; the `not accurate and ... percentDiff > 25` gate exists; the `duration > 0` guard exists on the queDuration call. **645 pytest passing** (633 baseline from imports.47 + 12 new). - Sibling fix to imports.44 — same operator-reported logo-render symptom on the second Kodi device (Android tablet). After imports.44 the served `pseudotv.m3u` correctly emitted `tvg-logo="http://192.168.2.217:50002/images/<basename>"` for the 61 previously-broken channels (live-confirmed via `curl http://127.0.0.1:50002/pseudotv.m3u`). But fetching one of those URLs returned `HTTP/1.1 200 OK` with `Content-Length: 0`. Trace: `server.py:1864` built `_allowed_roots = [os.path.abspath(LOGO_LOC), os.path.abspath(CACHE_LOC), os.path.abspath(MEDIA_LOC)]`, then joined the basename onto `_allowed_roots[0]`. The three `_LOC` constants are `special://...` URIs (LOGO_LOC at variables.py:33, CACHE_LOC at constants.py:262, MEDIA_LOC at constants.py:258 — all built via `os.path.join` on `getAddonInfo('profile')` / `ADDON_PATH`, neither of which is run through `xbmcvfs.translatePath` at module load). Python's `os.path.abspath` on a `special://...` string produces `<cwd>/special:/...` because POSIX treats `:` as a regular path char; the join then lands in a nowhere-tree, `FileAccess.stream` opens nothing, returns `b''`, and the response body is empty. The path-traversal guard at `server.py:1871` ALSO passes incorrectly because candidate and root share the bogus prefix, so the request looks "valid" all the way through. Dormant before imports.44: the only prior caller of `/images/` (variables.py:185, EPG `image://` art wrap) emits ABSOLUTE paths with a leading slash, taking the `img_path.startswith('/')` branch at server.py:1867 which sidesteps `_allowed_roots[0]` for candidate construction. imports.44's basenames go through the relative-path branch at line 1870 and expose the bug. **Fix is one-line per root**: wrap each in `FileAccess.translatePath(...)` so the abspath happens on the real filesystem path. The path-traversal check now compares real-filesystem prefixes and continues to enforce LOGO_LOC/CACHE_LOC/MEDIA_LOC confinement. No new pytest in this cycle (existing infra mocks BaseHTTPRequestHandler heavily; the surface is mechanical and live-verifiable via `curl -sI http://127.0.0.1:50002/images/<encoded-basename>`). Verifies as: pre-fix `HTTP/1.1 200 OK` + `Content-Length: 0`; post-fix `HTTP/1.1 200 OK` + `Content-Length: <real bytes>`.

- Fix runaway M3U render loop that grew `pseudotv.m3u` from ~150 KB to 1.6 GB and OOM-killed Kodi (anon-rss ≈ 6.8 GB on an 8 GB Pi5 → kernel OOM-killer → kodi-standalone crash loop). Root cause: `renderers.render_m3u`'s optional-attrs loop iterated `M3U_TEMP` keys without skipping the keys already emitted by the explicit format string (channel-id / tvg-chno / tvg-id / tvg-name / tvg-logo / group-title / radio / catchup) or on dedicated lines (label after the EXTINF comma; url on its own standalone line). Of those redundantly-emitted keys, `group` was the load-bearer: stations carry `group` as a Python list (e.g. `['Adult Swim', 'PseudoTV Live (imports)']` for Custom channels auto-grouped by both the channel-specific group and the addon-default group). The optional loop passed the list through `_m3u_attr_escape(value)` which does `str(value)` — Python's `str()` of a list returns the repr form `"['Adult Swim', 'PseudoTV Live (imports)']"` with a LITERAL COMMA between the elements. The rendered EXTINF then contained `group="['Adult Swim', 'PseudoTV Live (imports)']"` — a comma INSIDE a quoted attribute value. On the next service start (or any M3U._load re-parse), `m3u.py:_load`'s label regex `,(.*)` captured from the FIRST comma in the line — but that comma was now INSIDE the `group="..."` value, not the EXTINF name separator. `mitem['label']` ended up holding the entire EXTINF tail (`' 'PseudoTV Live (imports)']" radio=... catchup-source=... provider=... ,Display`). Next render: that giant label was emitted both as an optional `label="..."` attribute (with `"` → `%22` URL-encoded) AND as the raw display-name after the line's final comma → one EXTINF line size doubled per render→reload→render cycle. With Builder + chkImports + chkChanged all triggering renders, the doubling fires multiple times per minute; ~22 doublings × 442 bytes initial → 1.6 GB observed on disk. `pvr.iptvsimple` then tried to parse the 1.6 GB single-line M3U on Kodi startup (28.4-second `LoadPlayList` already audible in the previous "Playlist Loaded - 28437 (ms)" log line) which ballooned the Kodi process to ~6.8 GB anon RSS and got it OOM-killed. systemd's kodi-standalone wrapper auto-restarted, the next instance hit the same bloat and OOMed in ~25s, repeat indefinitely. Five-piece fix: (1) NEW module-level frozenset `renderers._EXPLICIT_M3U_KEYS = {'id', 'number', 'name', 'logo', 'group', 'radio', 'catchup', 'label', 'url'}` enumerates the keys ALREADY emitted by render_m3u's explicit format string or on dedicated locations. The optional-attrs loop now skips these via `if key in _EXPLICIT_M3U_KEYS: continue` so they're not re-emitted as bare-key attributes. Eliminates the corruption vector entirely — no comma can leak into a quoted attribute value via the `group` list, because `group` is no longer emitted as a redundant bare-key attribute. (2) Defense in depth in the same optional-attrs loop: list/tuple-typed values are normalized to ';'-joined strings BEFORE `_m3u_attr_escape` (`if isinstance(value, (list, tuple)): value = ';'.join(str(x) for x in value)`). Matches how `group-title` is rendered above (`_m3u_attr_escape(';'.join(station.get('group') or []))`). Future-proofs against a future M3U attribute happening to be list-typed reopening the bug — e.g., if anyone decides `provider-countries` should become a list of country codes per M3U convention, the renderer emits `provider-countries="US;CA;MX"` (semicolon-joined, parser-safe) instead of `provider-countries="['US', 'CA', 'MX']"` (Python repr, comma-embedded, corruption vector). (3) Defense in depth in `m3u.py:_load`'s label regex: changed from `,(.*)` to `(?:.*"|^#EXTINF:[^,]*),(.*)$`. The new regex anchors on the EXTINF separator (closing `"` of last attribute followed by `,`), not on the FIRST `,`. So even if a future external-source M3U arrives with a comma-bearing attribute value (rare but possible — some IPTV providers emit non-strict M3U with commas in display-names or descriptions), the parser correctly extracts the actual display-name. Falls back to first-comma split for malformed lines with no quoted attributes (`#EXTINF:-1,BareDisplay`). (4) Same regex fix applied to `m3u.parseExternalSource`'s `EXTINF_PATTERNS['label']` — the live-import EXTINF parser used a separate regex map that mirrored `_load`. Jitter ±12.5% on each computed delay prevents the thundering herd when many imports fail in the same cycle (e.g., LAN outage causes all sources to time out simultaneously, then all retry at exactly 60s without jitter). The bug: two threads (typically _onPlay @threadit worker + Monitor._chkIdle's __chkOverlay) could both observe `self.overlay = None`, both create an Overlay instance, both call open() — but the second one's open() bailed on the PROPERTIES.isRunning('Overlay') guard at overlay.py:248, leaving its channelBug control un-added. Meanwhile self.overlay was already overwritten to point at the second (phantom) Overlay. The first Overlay's channelBug control was already added to xbmcgui.Window(12005) by its open() call — that control persisted for the rest of the Kodi session, showing the previous channel's logo on top of every subsequent channel. v.26's chid-aware idempotency at the same site doesn't help here because it only fires when self.overlay is not None; the initial-create race happens BEFORE any overlay exists. Operator-visible symptom: previous channel's logo stuck on top of next channels. Live-verified across ~7 zaps after restart: open/close counts now match (modulo currently-active), _addControl/_delControl counts match, zero leaked controls. Also moved Overlay.cntrlManager from class scope to __init__ (instance attr) — defense in depth against any future direct Overlay() construction outside toggleOverlay's lock.

v.0.8.0+imports.17
- HTTP socket-release fix. server.py:HTTP.run() now calls self._server.server_close() immediately after self._server.shutdown(). BaseServer.shutdown() stops the serve_forever request loop but does NOT release the listening socket; the socket stays in LISTEN state until server_close() is called. Without it, every chkPVRRefresh→HTTP.pendingRestart=True cycle leaked the listening socket — the next chkHTTP's _chkPort(50002) saw the old fd still bound, failed the bind (SO_REUSEADDR doesn't override a peer's LISTEN-state socket — only TIME_WAIT), retried 10× over 5s, fell back to 50003, and fired the "port 50002 in use, 50003 available" notification toast every ~5 minutes during normal operation. Proof: lsof showed two kodi.bin-owned LISTEN fds on the same process — fd=27 on 50002 (leaked), fd=88 on 50003 (current). Live-verified post-restart: pendingRestart→shutdown→server_close→rebind cycle completes with `_chkPort 50002 (0 retries)`, zero toasts. The pre-existing _chkPort retry logic in server.py was a workaround designed to mask socket-release lag from cross-process Kodi restarts (TIME_WAIT) — never the in-process LISTEN-state leak this fixes. With imports.17 the retry loop is now mostly cosmetic for the cold-restart case.

v.0.8.0+imports.16
- Three-part services.py thread-safety hardening, all defensive. (1) De-nested _chkCallback as a method on Player (was a closure inside _onIdle) and added a CAS gate: snapshot self.playingItem at entry into a local ref `state`, resolve callback against `state`, publish (`state['callback'] = callback`) only if `self.playingItem is state` (the dict ref hasn't been swapped under us by another thread). Lock-free CAS analog. Closes a race where an _onPlay @threadit worker could swap self.playingItem between the idle thread's read and write, contaminating fresh state with a stale-context callback resolution. (2) Moved Player.pendingItem and Player.playingItem from class-level mutable defaults to __init__ instance attrs. Standard Python footgun; if multiple Player instances ever co-existed, they'd silently share state. (3) Cleaned up _onPlay's redundant non-PTV double-write — the non-PTV branch wrote self.playingItem at line 389 then fell through to line 432 which wrote it again (functionally harmless but the structure obscured the v.26 ordering constraint). Restructured: non-PTV branch now early-returns after toggleOverlay(False) + lastSubState; PTV body de-indented (no more `if playingItem.get('isPseudoTV'):` wrapper since non-PTV returned). v.26 race-fix ordering preserved exactly. The 2026-05-12 audit explicitly rejected an RLock around player state — it would conflict with Kodi's "callbacks must be non-blocking" guidance, the existing surgical fixes cover three of four identified race classes, and only the _chkCallback writer-races-writer was a real bug. v.18 later added Player._overlay_lock for a different race class (initial-create) where a lock IS the right tool.

v.0.8.0+imports.15
- XMLTVS.cleanSelf now cross-references channels.json to drop orphan Custom channels from pseudotv.xml. Symmetric to M3U._verify at m3u.py:471-475. The bug: when an operator deleted a Custom PseudoTV channel via the UI, M3U's cleanSelf path correctly dropped the channel from pseudotv.m3u, but XMLTVS.cleanSelf had no equivalent channels.json cross-reference — orphan <channel> + <programme> entries remained in pseudotv.xml. Operator-reported live during the 2026-05-12 PM session: "Five Fingers of Death" was deleted via the UI, M3U showed it gone, but pseudotv.xml still carried 181 orphan programmes (~748 KB on disk). The fix's first chkImports cycle auto-healed the live state. Recordings exempt from the cross-reference (they're live-only in M3U/XML, intentionally absent from channels.json).

v.0.8.0+imports.12
