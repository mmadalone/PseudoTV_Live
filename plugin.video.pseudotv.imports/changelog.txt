### NOTICE: plugin.video.pseudotv.imports is a sibling fork of plugin.video.pseudotv.live, adding native M3U/XMLTV ingestion + a web dashboard at port 50002. Versions are 0.8.0+imports.NN. Pre-fork upstream history lives in plugin.video.pseudotv.live/changelog.txt. ####

v.0.8.0+imports.19
- Clear-key mismatch fix in `_chkPropTimer`. Added Properties.clrPropTimer(key) in kodi.py mirroring set/getPropTimer's `if not key.startswith(ADDON_ID): key = '%s.%s'%(ADDON_ID, key)` prelude; tasks.py:340 now calls clrPropTimer(key) instead of clrEXTProperty(key). Root cause: setPropTimer and getPropTimer both prepend the addon-ID namespace, but the matching clrEXTProperty in `_chkPropTimer` did not — so `Window(10000).clearProperty('chkPVRRefresh')` tried to clear a key that was never set; the actual `plugin.video.pseudotv.imports.chkPVRRefresh` stayed True forever after first set. Effect on live data: in a single 90-minute playback session the property was set True 7 times (from genuine triggers: builder, manager, default.py template-fix, etc.) but read True 46 times and read False 0 times. Each True-read in chkQueTimer's 15-second epoch tick re-queued chkPVRRefresh, which scheduled HTTP.pendingRestart=True 15 s later, which cycled the HTTP server — operator-visible as the recurring green `madteevee: Online` toast during playback, manager.html unreachable in ~15 s windows (~30 % of the time at peak — verified live with curl on 2026-05-12 at 06:10–06:11), and a flurry of `HTTP: run, _shutdown/pendingRestart` errors in kodi.log. The bug also affects chkChanged (the only other `_chkPropTimer` consumer) but symptoms were quieter because chkChanged is only triggered by operator edits and the v.44 `Builder.isRunning` defer path masked the re-queue churn while builds were in flight. Upstream `.live` has the same bug at tasks.py:169 + kodi.py:656; fork-only patch per fork-only-no-upstream policy. The earlier v.46 madteevee fix dropped the `else:` re-arm self-loop in chkPVRRefresh's brute-deferred branch (a different self-loop in the same area); this fix closes the underlying clear-key bug that was driving the remaining 15 s churn even after v.46.

v.0.8.0+imports.18
- toggleOverlay thread-safety fix. Added Player._overlay_lock = Lock() in services.py and wrapped toggleOverlay's body with `with self._overlay_lock:`. The bug: two threads (typically _onPlay @threadit worker + Monitor._chkIdle's __chkOverlay) could both observe `self.overlay = None`, both create an Overlay instance, both call open() — but the second one's open() bailed on the PROPERTIES.isRunning('Overlay') guard at overlay.py:248, leaving its channelBug control un-added. Meanwhile self.overlay was already overwritten to point at the second (phantom) Overlay. The first Overlay's channelBug control was already added to xbmcgui.Window(12005) by its open() call — that control persisted for the rest of the Kodi session, showing the previous channel's logo on top of every subsequent channel. v.26's chid-aware idempotency at the same site doesn't help here because it only fires when self.overlay is not None; the initial-create race happens BEFORE any overlay exists. Operator-visible symptom: previous channel's logo stuck on top of next channels. Live-verified across ~7 zaps after restart: open/close counts now match (modulo currently-active), _addControl/_delControl counts match, zero leaked controls. Also moved Overlay.cntrlManager from class scope to __init__ (instance attr) — defense in depth against any future direct Overlay() construction outside toggleOverlay's lock.

v.0.8.0+imports.17
- HTTP socket-release fix. server.py:HTTP.run() now calls self._server.server_close() immediately after self._server.shutdown(). BaseServer.shutdown() stops the serve_forever request loop but does NOT release the listening socket; the socket stays in LISTEN state until server_close() is called. Without it, every chkPVRRefresh→HTTP.pendingRestart=True cycle leaked the listening socket — the next chkHTTP's _chkPort(50002) saw the old fd still bound, failed the bind (SO_REUSEADDR doesn't override a peer's LISTEN-state socket — only TIME_WAIT), retried 10× over 5s, fell back to 50003, and fired the "port 50002 in use, 50003 available" notification toast every ~5 minutes during normal operation. Proof: lsof showed two kodi.bin-owned LISTEN fds on the same process — fd=27 on 50002 (leaked), fd=88 on 50003 (current). Live-verified post-restart: pendingRestart→shutdown→server_close→rebind cycle completes with `_chkPort 50002 (0 retries)`, zero toasts. The pre-existing _chkPort retry logic in server.py was a workaround designed to mask socket-release lag from cross-process Kodi restarts (TIME_WAIT) — never the in-process LISTEN-state leak this fixes. With imports.17 the retry loop is now mostly cosmetic for the cold-restart case.

v.0.8.0+imports.16
- Three-part services.py thread-safety hardening, all defensive. (1) De-nested _chkCallback as a method on Player (was a closure inside _onIdle) and added a CAS gate: snapshot self.playingItem at entry into a local ref `state`, resolve callback against `state`, publish (`state['callback'] = callback`) only if `self.playingItem is state` (the dict ref hasn't been swapped under us by another thread). Lock-free CAS analog. Closes a race where an _onPlay @threadit worker could swap self.playingItem between the idle thread's read and write, contaminating fresh state with a stale-context callback resolution. (2) Moved Player.pendingItem and Player.playingItem from class-level mutable defaults to __init__ instance attrs. Standard Python footgun; if multiple Player instances ever co-existed, they'd silently share state. (3) Cleaned up _onPlay's redundant non-PTV double-write — the non-PTV branch wrote self.playingItem at line 389 then fell through to line 432 which wrote it again (functionally harmless but the structure obscured the v.26 ordering constraint). Restructured: non-PTV branch now early-returns after toggleOverlay(False) + lastSubState; PTV body de-indented (no more `if playingItem.get('isPseudoTV'):` wrapper since non-PTV returned). v.26 race-fix ordering preserved exactly. The 2026-05-12 audit explicitly rejected an RLock around player state — it would conflict with Kodi's "callbacks must be non-blocking" guidance, the existing surgical fixes cover three of four identified race classes, and only the _chkCallback writer-races-writer was a real bug. v.18 later added Player._overlay_lock for a different race class (initial-create) where a lock IS the right tool.

v.0.8.0+imports.15
- XMLTVS.cleanSelf now cross-references channels.json to drop orphan Custom channels from pseudotv.xml. Symmetric to M3U._verify at m3u.py:471-475. The bug: when an operator deleted a Custom PseudoTV channel via the UI, M3U's cleanSelf path correctly dropped the channel from pseudotv.m3u, but XMLTVS.cleanSelf had no equivalent channels.json cross-reference — orphan <channel> + <programme> entries remained in pseudotv.xml. Operator-reported live during the 2026-05-12 PM session: "Five Fingers of Death" was deleted via the UI, M3U showed it gone, but pseudotv.xml still carried 181 orphan programmes (~748 KB on disk). The fix's first chkImports cycle auto-healed the live state. Recordings exempt from the cross-reference (they're live-only in M3U/XML, intentionally absent from channels.json).

v.0.8.0+imports.14
- chkImports defers when Builder.buildChannels is running. Symmetric to the chkChanged defer at tasks.py:336 and chkPVRRefresh defer at tasks.py:795. The kick-loop blocker-chain in _startImportsThread (tasks.py:125-141) is extended with a 'builder-running' branch — precedence: playback > syncAll-running > builder-running > None. Closes an in-process race where a Builder.buildChannels write to pseudotv.xml could land mid-Imports.syncAll merge, with the imports.py:916-955 Custom-merge-from-disk workaround compensating at the cost of an extra 30 MB disk re-parse per cycle. With imports.14 the avoidable in-process race is gone; the workaround only fires now for genuine cross-process scenarios (context_record.py runs in a separate process, operator hand-edits).

v.0.8.0+imports.12
- WRITER_LOCK module (writer_lock.py): a process-wide threading.RLock around M3U/XMLTV render-then-os.replace operations. Defense in depth around existing PROPERTIES.isRunning gates. Doesn't protect against cross-process state divergence (context_record.py runs in a separate process and doesn't honor this lock), but eliminates the in-process race window where two threads (Builder + chkImports daemon) could both be mid-render against pseudotv.xml / pseudotv.m3u. Zero `writer_lock: TIMEOUT` warnings observed in production across the imports.12-18 lifetime.
